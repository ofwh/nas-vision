# API 规范

本文统一规定 API 的方法、路径、请求、鉴权、分层、响应和错误处理。第三方协议适配与二进制传输的例外见[协议适配边界](#协议适配边界)。

## 方法与路径

- 自有业务接口统一使用 POST，业务参数放在请求体中，不通过 RESTful 方法或动态路径表达业务操作。
- 不需要登录的自有业务接口统一放在 `/api/public` 下。
- 新增和更新合并为一个接口，通过请求体中可选的 `id` 区分：带 `id` 时更新，不带时新增。

## 请求

- 请求体类型命名为 `<模块>XxxParams`。
- API 层使用 `readParams<T>` 解析 JSON 请求体，使用 `readForm` 解析表单；解析失败返回统一错误信封。
- 类型断言不代表运行时校验。字段类型、取值范围及业务约束由 service 校验，API 不做逐字段校验。

## 登录与会话

- 受保护接口的登录检查统一由 `proxy.ts` 处理，API 不重复检查。
- 公开接口需要按登录状态返回不同数据时，由 API 获取 session，并交给 service 处理。
- 认证协议入口的会话建立与验证由对应认证协议处理。

## 分层

调用链 `api -> services -> repositories -> db`，按需复杂度实现；**api 和 services 两层必须有**。

- **api** —— 请求体转强类型、调 service、拼 `BaseResponse`。不写业务判断，不直接碰 db / repositories。
- **services** —— 负责业务规则与参数校验。不写 SQL，读写交给 repository。
- **repositories** —— 只跟库打交道，不做业务判断，只被 services 调用。
- **db** —— drizzle 实例与 schema。

service 的约定：

- 方法名用简洁动词：list / create / update / save / updateStatus / remove / sort。
- 既导出单个方法，也通过 default 导出全量方法，调用方写 `service.xxx(...)`。

## 响应契约

自有业务接口使用 `lib/api` 的 `BaseResponse<T>` 返回业务结果，HTTP 状态为 200，以响应体 `code` 判断成败。

| 场景 | code       | data     | message        | error                                  |
| ---- | ---------- | -------- | -------------- | -------------------------------------- |
| 成功 | `0`        | 业务结果 | 默认 `OK`      | 不返回                                 |
| 失败 | 数值错误码 | `null`   | 本地化错误文案 | `{ code: '<模块>.<错误名>', message }` |

失败时 `message` 与 `error.message` 相同。JSON / 表单解析失败也使用此信封，错误响应不暴露凭据或原始异常栈。

## 错误归属

| 范围         | 定义位置                                              | 响应处理          |
| ------------ | ----------------------------------------------------- | ----------------- |
| 公共错误     | `lib/api/codes.ts`、`lib/api/messages/{locale}.json`  | `lib/api`         |
| 宿主业务错误 | `lib/errors/<业务>.ts`，经 `lib/errors/index.ts` 聚合 | `lib/api`         |
| 插件框架错误 | `lib/plugins/errors.ts`                               | 宿主 API / 分发层 |
| 插件私有错误 | `components/plugins/<插件>/api/errors.ts`             | 插件自身 API      |

service 判断业务错误，API 负责响应适配。公共模块不导入、聚合或导出插件私有错误码、类型与文案。插件私有业务接口仅通过插件根入口的 `api` 接入宿主。

宿主业务错误文件导出 `codes`、`messages`；业务层通过 `appError(code, params?)` 表达错误，API 用 `errorResponse(error)` 构造信封。服务端需要当前语言时使用 `lib/api/server` 的 `errorResponse`；客户端本地错误文案使用 `errorMessage(error, locale)`。

插件 handler 返回 `Result<Response>`：`{ ok: true, value: response }` 表示响应已构造，宿主直接转交；业务成败仍看响应体 `code`。失败 Result 仅携带宿主已知错误，例如公共解析错误；插件私有业务错误先在插件 API 内转换为错误信封。

## 编号与文案

### 公共错误

公共错误使用四位数 `1000`–`9999`，表达与具体业务无关的通用失败原因，与 HTTP 状态无关。分配前优先复用语义一致的已有错误；具体业务约束失败使用所属业务的七位错误码。

### 业务错误

七位业务码按 `<业务><模块><错误码>` 组成：

| 段     | 位数 | 范围        | 唯一范围 |
| ------ | ---- | ----------- | -------- |
| 业务   | 2    | `10`–`99`   | 全局     |
| 模块   | 2    | `01`–`99`   | 所属业务 |
| 错误码 | 3    | `000`–`999` | 所属模块 |

数值为 `业务码 * 100000 + 模块码 * 1000 + 错误码`。宿主业务（含插件框架）使用 `10`–`49`，具体插件使用 `50`–`99`，分别从 `10` 和 `50` 开始分配。同一业务保持业务码不变，插件独立分配业务码，不占用插件框架的业务码。

#### 业务码占用登记

业务码一经使用或预留，必须立即回写下表，注明所属业务及错误定义位置；预留但尚未定义错误时，定义位置填“待定义”。已有登记不得删除或转给其他业务，停用后仍保留占用。此表仅登记两位业务码，具体模块码、错误编号、标识与文案由源码维护。

| 业务码 | 所属业务                             | 错误定义位置                                 |
| ------ | ------------------------------------ | -------------------------------------------- |
| `10`   | 配置                                 | `lib/errors/config.ts`                       |
| `11`   | 账户                                 | `lib/errors/account.ts`                      |
| `12`   | 应用管理                             | `lib/errors/apps.ts`                         |
| `13`   | 插件框架                             | `lib/plugins/errors.ts`                      |
| `14`   | iframe                               | `lib/errors/iframe.ts`                       |
| `15`   | 上传                                 | `lib/errors/upload.ts`                       |
| `16`   | Immich 插件（停用保留，不再分配）    | —                                            |
| `17`   | Navidrome 插件（停用保留，不再分配） | —                                            |
| `50`   | Immich 插件                          | `components/plugins/immich/api/errors.ts`    |
| `51`   | Navidrome 插件                       | `components/plugins/navidrome/api/errors.ts` |
| `52`   | 天气插件                             | `components/plugins/weather/api/errors.ts`   |

### 分配流程

业务码占用以本章登记表和源码共同核对；具体错误编号、标识和文案以错误定义文件为准，不在文档重复列举。发现源码使用但未登记的业务码时，先补全登记再分配；登记与源码归属冲突时，先解决冲突，不得继续占用冲突业务码。

数值错误码全局唯一，错误标识在所属命名空间内唯一，各语言错误键必须一致。每个编号在每种语言下对应一个固定模板，调用方不得覆盖；动态信息使用命名参数插值。

1. 分配前检查本章业务码占用登记，以及 `lib/api/codes.ts`、`lib/errors/*.ts`、`lib/plugins/errors.ts` 和 `components/plugins/*/api/errors.ts` 中的现有定义。
2. 公共错误优先复用已有类别；确需新类别时，在四位范围内从现有最大编号递增分配，首次从 `1000` 开始。
3. 新业务在所属分配区间内，按登记表与源码中已使用或预留的最大业务码递增分配：宿主业务使用 `10`–`49`，首次从 `10` 开始；具体插件使用 `50`–`99`，首次从 `50` 开始。分配后立即回写本章业务码占用登记，再添加具体错误定义。已有业务新增模块，在该业务最大模块码后递增分配，首次从 `01` 开始。
4. 同一明确错误复用已有编号；新增错误在所属模块最大错误码后递增分配，首次从 `000` 开始。超出任一段范围时停止分配，不回填历史空号或重排已有编号。
5. 将数值码、稳定的 `<模块>.<错误名>` 标识和各语言文案写入对应定义位置。

已使用编号不得重排或复用；废弃错误在原定义文件保留编号，不再用于新错误。新增后核对全局数值无冲突；不同业务原因不能折叠为公共参数错误或公共请求失败。

### 保存与接入

- 公共错误：数值与标识写入 `lib/api/codes.ts`，文案写入 `lib/api/messages/{locale}.json`，不加入具体业务原因。
- 宿主新业务：在 `lib/errors/<业务>.ts` 导出 `codes`、`messages`，接入 `lib/errors/index.ts` 的聚合，供 `lib/api` 推导类型、映射编号与格式化文案。已有业务新增模块或错误仍写入所属业务文件。
- 插件框架：仅在 `lib/plugins/errors.ts` 维护框架自身错误。
- 具体插件：数值与错误类型保存在 `components/plugins/<插件>/api/errors.ts`，多语言文案集中在插件自身 `i18n/` 目录，由插件 API 按当前语言读取并适配为错误信封。按需拆出私有 `api/response.ts`，不接入宿主 `lib/errors`、公共 `ErrorCode` 或公共文案导出。没有业务错误时无需创建这些文件。

## 协议适配边界

第三方协议适配接口可按协议要求保留请求方法、路径、响应结构、状态码及响应头。二进制传输保留必要的传输语义。例外仅在对应适配层处理，不扩展为普通业务接口规则；具体约束记录在所属模块文档。

本地业务错误仍转换为统一信封。替换响应体时，必须同步处理与响应体相关的响应头，并保留协议所需的 cookie 等信息。适配层不得向客户端暴露原始异常栈或敏感信息。

登录检查与会话处理遵守本文[登录与会话](#登录与会话)的规定。
